# 0015. Проверка deliverable арт-директором

Статус: принято, 2026-10-19

## Контекст

На deliverable съёмки назначают одного или нескольких исполнителей: креаторов и мобилографов (ADR 0007). До сих пор работа над deliverable была общей: один черновик и одна нумерация версий на всех (ADR 0012), один статус. Арт-директору нужен экран проверки (Figma «SCREEN:s_review Shoot / Review deliverable»). На нём он видит работу каждого исполнителя, одобряет её или просит изменения, а когда одобрено всё, отправляет deliverable бренду.

## Решения

### Работа каждого исполнителя отдельно

- У каждого исполнителя свой черновик и своя нумерация версий: уникальный ключ `task_versions` теперь `(deliverable_id, author_id, number)`. Исполнитель видит на странице задачи только свои версии, арт-директор видит отправленные версии всех.
- `shoot_deliverable_assignees.status` хранит статус исполнителя. Он начинается с `to_shoot`, первый файл черновика переводит его в `in_progress` (если черновик опустел, а версий ещё нет, статус возвращается в `to_shoot`). Submit for review ставит `needs_review`, решение арт-директора ставит `needs_changes` или `approved` (с ADR 0016 статус после решения считается по всем версиям исполнителя). Редактирование съёмки статусы оставшихся исполнителей не сбрасывает.
- Решение хранится на версии: `review` (`approved` | `changes_requested`), `reviewed_at`, `feedback` (Feedback for creator, до 1000 символов, для Request changes обязателен). Исполнитель видит решение и feedback на своей версии.
- В My tasks статус задачи креатора — это его собственный статус, а не статус deliverable: одобренная работа одного не висит в Needs review из-за другого, а просьба об изменениях видна именно тому, кого она касается. У арт-директора статус задачи — по-прежнему статус deliverable.

### Статус deliverable собирается из статусов исполнителей

После каждого изменения статуса исполнителя статус deliverable пересчитывается (`app/shoots/statuses.py`):

1. кто-то ждёт проверки → `needs_review`;
2. иначе кто-то дорабатывает → `needs_changes`;
3. иначе одобрены все → `needs_review`: deliverable ждёт арт-директора, ему осталось отправить его бренду;
4. иначе кто-то начал → `in_progress`, иначе `to_shoot`.

`approved` означает «отправлен бренду», и после этого пересчёт его не трогает.

Форма съёмки:

- статус из формы задаётся только у нового deliverable (селект в Add deliverable), и `approved` среди вариантов нет: его ставит только Send to brand (иначе 422). У сохранённого deliverable форма статус не присылает: прислала — 422;
- статус сохранённого deliverable, над которым кто-то работал (в том числе снятый сейчас исполнитель), при сохранении формы пересчитывается из статусов оставшихся исполнителей. Отправленный бренду остаётся отправленным;
- статус исполнителя при сохранении формы берётся по его версиям, поэтому снятый и снова назначенный исполнитель получает свою работу обратно. Сохранение формы ждёт блокировки deliverables, под которой исполнители отправляют версии.

Миграция: статусы исполнителей восстанавливаются по их версиям, статус начатых deliverables пересчитывается. Общий черновик до миграции становится черновиком того, кто его начал; номера уже существующих версий сохраняются, поэтому первая своя версия исполнителя может быть не V1.

Если арт-директор одобрил версию, пока исполнитель собирал черновик следующей, этот черновик остаётся неотправленным: работа уже одобрена.

## Не входит в эту итерацию

Сторона бренда (что он видит после отправки), уведомления исполнителю о решении, комментарии к отдельным файлам, свой плеер из Figma (пока у видео стандартные контролы браузера).
