# 0002. Суперадмин и связки бренд ↔ арт-директор ↔ креатор

Статус: принято, 2026-10-03

## Контекст

Бренд создаёт продукт и назначает на него одного или нескольких арт-директоров. Арт-директор работает с несколькими брендами, у бренда может быть несколько арт-директоров. Арт-директор создаёт съёмки и назначает на них креаторов из своей команды. Кто с кем работает (бренд с арт-директорами, арт-директор с креаторами), решаем мы, а не пользователи. Для этого нужен суперадмин и отдельная страница: все пользователи, их связки и назначение.

Суперадмина нельзя создать через регистрацию.

## Решения

### Админ — флаг, а не роль

`users.is_admin: bool`, по умолчанию `false`.

В `Role` админа не добавляем: `PATCH /api/me/onboarding` принимает любое значение `Role`, и любой пользователь на онбординге смог бы выбрать себе роль админа. Флаг не принимает ни одна публичная схема. По смыслу `role` описывает, кто ты внутри продукта, а админ находится вне его.

Админ — служебный аккаунт, в продукт он не входит:

- `role = null`, `status = approved`. CHECK-ограничение `admin_has_no_role` в БД не даёт совместить флаг с ролью.
- `ApprovedUser` пропускает только не-админов, поэтому продуктовые эндпоинты админу закрыты, даже если в них забыли `require_role`.
- Онбординг админу недоступен: его статус `approved`, а онбординг меняется только в `onboarding`.

### Админ создаётся CLI-командой

```
uv run python -m app.admin.create_admin admin@example.com
```

Пароль запрашивается дважды через `getpass` (в историю shell не попадает), минимум 12 символов, хэш argon2 тем же кодом, что и при регистрации. Если админ с таким email уже есть, команда меняет ему пароль и удаляет все его сессии: это и есть восстановление доступа. Обычного пользователя админом команда не делает и завершается с ошибкой.

Запустить команду может только тот, у кого есть доступ к серверу и `DATABASE_URL`. Отвергнутые варианты: ручной `INSERT` (хэш и нормализация email вручную, легко ошибиться), сид в миграции (секрет в git), `ADMIN_EMAILS` в env (админом станет тот, кто первым зарегистрируется на этот email).

### Вход и сессии админа

- Вход только по паролю. Вход через Google на email админа отклоняется, иначе срабатывает привязка Google с перехватом аккаунта из ADR 0001.
- Сессия админа живёт `admin_session_ttl_hours` (12 часов) и не продлевается.
- Лимиты попыток входа те же, что у всех.
- `/api/me` отдаёт `is_admin`, фронт ведёт админа на `/admin`.

### API админки

- Всё под `/api/admin/*`, зависимость `AdminUser`. Без сессии `401`, с сессией не-админа `404`: существование админки не раскрываем.
- `GET /api/admin/users` — все пользователи, кроме админов, и все связки.
- `PUT /api/admin/brands/{brand_id}/art-directors/{art_director_id}` — назначить арт-директора бренду, повторный вызов ничего не меняет.
- `PUT /api/admin/art-directors/{art_director_id}/creators/{creator_id}` — то же для креатора арт-директора.
- `DELETE` по тем же путям — снять.

Список отдаётся целиком, без пагинации: пользователей пока десятки. Когда станет больше, добавим поиск и страницы на бэке.

### Связки

Две таблицы одного вида, обе many-to-many:

- `brand_art_directors (brand_id, art_director_id, assigned_by, assigned_at)`: у бренда несколько арт-директоров, арт-директор работает с несколькими брендами.
- `art_director_creators (art_director_id, creator_id, assigned_by, assigned_at)`: у арт-директора команда креаторов, креатор может быть в командах нескольких арт-директоров.

Первичный ключ — пара. При удалении пользователя связки удаляются каскадом. Бренд и креатор напрямую не связаны: креатор попадает к бренду через съёмки арт-директора.

Внешний ключ роль не проверяет, поэтому это делает сервис: обе стороны должны быть одобренными пользователями нужных ролей, иначе `422`. Роль после одобрения сама не меняется (ADR 0001), так что связка не может испортиться.

На продукт бренд позже сможет назначать только арт-директоров из своих связок, а арт-директор на съёмку — только креаторов из своей команды.

### Журнал действий

Таблица `admin_actions (id, admin_id, action, brand_id, art_director_id, creator_id, created_at)`: назначения и снятия обеих связок, заполнены колонки участников действия. Ссылки на пользователей хранятся без внешних ключей, чтобы история пережила удаление аккаунтов. Записи только добавляются. Повторное назначение или снятие несуществующей связки в журнал не пишутся.

### Подтверждение в интерфейсе

Каждое изменение подтверждается в модалке. Назначение: в модалке отмечают одного или нескольких пользователей (по запросу на каждого, вызовы идемпотентны), она показывает «X, Z будут работать с Y», и ничего не меняется до нажатия Assign. Снятие: крестик открывает отдельную модалку подтверждения.

Назначают со стороны владельца связки: бренду — арт-директоров, арт-директору — креаторов. Снять связку можно с любой стороны.

## Не входит в эту итерацию

2FA для админа, одобрение заявок из админки (пока через Telegram), смена ролей и блокировка пользователей, несколько уровней админов.
